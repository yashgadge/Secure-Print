# SecurePrint Ledger — Full From-Scratch Product Blueprint (Expanded)

## 1) Product Goal

SecurePrint Ledger is a role-based secure document distribution, print accountability, and forensic leak attribution system. The product must be designed from scratch so that every visible UI element, every backend action, every file action, and every investigative workflow is real, persistent, and traceable.

This is not a dashboard mockup. It is a working platform where:

* an admin uploads or creates secure documents,
* the system generates uniquely traceable print copies,
* operators print assigned jobs,
* leaked files can later be uploaded and scanned,
* the system recovers forensic identifiers,
* the origin of the leak can be attributed,
* every meaningful action is stored in a persistent database and audit trail.

The final product must feel like a complete enterprise system, not a template or demo.

---

## 2) Hackathon Problem Statement Alignment

The product should directly solve a real problem:

* secure distribution of official/exam documents,
* hidden traceability in every printed copy,
* accountability for printers and operators,
* leak detection and origin tracing,
* immutable record keeping,
* beginner-friendly operator/admin experience,
* optional reward/bounty workflow if the hackathon includes one.

### What judges should understand instantly

1. A master document is uploaded.
2. The system creates encoded copies for selected centers/operators.
3. Each printed copy carries a unique forensic identity.
4. A leaked copy can be scanned later.
5. The scanner identifies the original job, copy number, operator, printer, center, and batch.
6. The chain of custody is preserved.
7. The ledger/history proves what happened.
8. The whole system stays usable for non-technical users.

### Important design principle

The user should never need to understand the internals to use the system.
The forensic complexity should happen behind the scenes, while the UI stays simple and clear.

---

## 3) Product Principles

The build should follow these principles:

* **Real over decorative**: every visible button should perform a real action.
* **Persistent over temporary**: created data must survive refresh and restart.
* **Traceable over hidden**: every print copy must be attributable.
* **Simple over complex**: the UI should remain approachable.
* **Role-aware**: public, operator, and admin users each see only their allowed actions.
* **Audit-first**: all important actions create logs.
* **No fake data**: no hardcoded sample rows or non-working panels.

---

## 4) User Roles and What Each Role Can Do

### A) Public User / Leak Reporter

Public users need a simple portal for submitting suspicious or leaked files.

They can:

* upload a suspected leak file,
* receive a generated case ID,
* track the status of their case,
* see whether the file was matched to a known secure copy,
* see whether the case is under review, attributed, or eligible for follow-up.

They cannot:

* approve operators,
* manage print centers,
* access admin dashboards,
* view private operational data.

### B) Operator

Operators are the print execution layer.

They can:

* log in only if approved,
* view assigned jobs,
* see the current printer status,
* start, pause, resume, and complete print work,
* verify dispatch or seal/packet status,
* see their own job history and session state.

They cannot:

* approve themselves,
* view admin-only controls,
* access unrelated operator records,
* see data that is not assigned to them.

### C) Admin / Super Admin

Admins control the entire system.

They can:

* manage operators,
* manage centers, zones, and print nodes,
* upload master documents,
* configure forensic settings,
* generate batches and jobs,
* dispatch to operators and centers,
* preview and download encoded files,
* verify the embedded forensic markers,
* investigate leaks,
* review bounty/reward decisions,
* inspect ledger records,
* control security settings,
* view activity and audit logs.

## 7) End-to-End Workflows

### Workflow A — Secure Document Creation and Dispatch

1. Admin logs in.
2. Admin uploads a master PDF or DOCX.
3. Admin chooses center and operator.
4. Admin applies forensic settings.
5. Admin clicks Generate / Deploy.
6. Backend creates a batch and a job.
7. Encoded files are generated and stored.
8. PDF preview appears.
9. View/Download buttons become active.
10. Activity log updates.
11. Operator receives the assignment.

### Workflow B — Operator Print Execution

1. Operator logs in.
2. Operator sees assigned job.
3. Operator starts print.
4. Print session begins.
5. Operator can pause/resume/complete.
6. Dispatch verification can be recorded.
7. Printer status updates.
8. Activity and logs are written.

### Workflow C — Leak Discovery and Attribution

1. A leaked file is uploaded.
2. The scanner reads the file.
3. The embedded forensic payload is extracted.
4. The system identifies the original operator/center/batch/copy.
5. The confidence score is calculated.
6. Timeline and proof are stored.
7. The user/admin sees the recovered attribution.

### Workflow D — Reward / Bounty Handling

1. A case is reviewed.
2. Eligibility is checked.
3. The case can be approved or rejected.
4. If approved, the reward flow is recorded.
5. The ledger history updates.

## 9) File Storage and Forensic File Handling

### Upload locations

* `uploads/original/` — master files and original submissions
* `uploads/generated/&lt;jobId&gt;/` — generated encoded copies
* `uploads/leaks/&lt;caseId&gt;/` — leak uploads and evidence files
* `uploads/reports/` — exported reports

### File lifecycle

1. User uploads or admin uploads a file.
2. The original file is stored.
3. The system generates encoded copies.
4. A preview URL is generated.
5. View and download become available.
6. Later, a leaked copy can be uploaded and scanned.
7. The scanner recovers metadata and attributes the source.

### File safety rules

* use unique filenames,
* avoid overwriting unless intentionally regenerating,
* verify generated files exist before enabling actions,
* preserve files after server restart.
